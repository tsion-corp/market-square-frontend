# CLAUDE.md — Market Square Frontend

Market Square: the social, discovery, streaming and ARK Store surface of the Ark/WorldStreet platform. Sibling app to `../wsws-frontend` — follow its conventions; do not import from it.

## Tech Stack
- Next.js (App Router) + React 19 + TypeScript, pnpm
- Tailwind CSS v4 — theme in `app/globals.css` via `@theme inline`; NO component library
- Auth: Decane (`decane-connect-kit` client, `decane-node` server verification). Privy remains only for the migration window: the BFF still accepts pre-migration Privy sessions, and `/move-account` signs into the OLD Privy account once to link it (`POST /v1/user-management/link`, contract in tsionark-monorepo `apps/market-square/llms-link.txt`)
- Server state: TanStack Query v5. NO global state manager (no Redux/Zustand); React local state for UI
- Validation at boundaries: zod v4. Toasts: sonner. Animation: motion

## Architecture (layers, imports point downward only)
- `app/` — routes + BFF route handlers. Owns no business logic
- `features/` — vertical slices (`feed`, `streams`, `store`, `profile`); slices NEVER import each other; each exposes only its `index.ts` barrel
- `components/ui/`, `hooks/` — shared presentation/behaviour
- `lib/` — pure cross-cutting: api client, envelope, formatters, brand

## API rules
- Backend envelope: `{ success: true, data } | { success: false, error: { code, message, details? } }` — `unwrap<T>()` in `lib/api/envelope.ts` throws typed errors
- Data flow: component → hook (useQuery/useMutation) → feature api client → `app/api/market-square/[...path]` BFF proxy → `${WSAPI_BASE_URL}/v1/market-square/*`
- Components NEVER call fetch directly or hold base URLs. The BFF verifies the session (Decane, or a legacy Privy one) and forwards `Authorization`
- **`pnpm check:public-routes` also catches PHANTOM ROUTES** — paths the frontend calls that the spec does not document at all. The public/gated diff can only judge routes the spec knows about, so a path invented ahead of the backend was invisible to it; `search`, `quote`, `mentions` and `operations` were each called from the client before they existed, surfacing as mystery 404s rather than build errors. Every request goes through `msApi.<method>("/path")`, so the call sites are collected by regex, `${...}` and `{param}` are normalised to the same token, and the method+path pairs are diffed against the spec. Deliberate ahead-of-backend calls go in `PENDING_ROUTES` with a reason and are deleted when the route ships — same discipline as `KNOWN_MISMATCHES`. **Routes the BFF answers ITSELF go in `BFF_HANDLED`**, because they will never appear in the upstream spec and that is correct rather than a gap — `GET /mentions/search` is rewritten onto `/search?type=people` and reshaped, so the request never reaches the service. A check that cries wolf on those trains everyone to ignore it. Two bounded limits: a path assembled entirely from a variable cannot be read statically (only `lib/api/upload.ts`, whose three routes are documented upstream), and raw BFF-prefixed `fetch` calls are checked by path rather than method
- **Run `pnpm check:public-routes` whenever routes change.** It fetches the backend's `openapi.json` and diffs the public-GET set against `isPublicGet` in BOTH directions, exiting non-zero with a readable diff. `MS_API_BASE=… pnpm check:public-routes` (or `--base`) points it at another environment. It needs a live backend, so it is not in `pnpm test` — the hand-written table in `lib/api/public-routes.test.ts` covers the same ground offline. **Keep both.** Three public routes (`categories`, `search`, `topics`) reached production gated at 401 before this existed, each found only when somebody hit the 401 by hand
- Which GETs a signed-out visitor may read lives in `lib/api/public-routes.ts` (`isPublicGet`), and its **source of truth is the backend's `openapi.json`**. A GET is public when the spec lets an **anonymous** caller make it: `security` is a list of alternatives OR'd together, and an **empty object is the alternative that requires nothing** — so both a missing `security` and `[{}, {bearerAuth: []}]` mean public. That second shape is "optional auth", which is what every public Market Square GET actually is. Reading any non-empty array as secured reported twelve false failures (including `/feed` and `/search`) the day the backend started spelling optional auth out properly. `lib/api/public-routes.test.ts` asserts that table in **both** directions — a route that silently becomes secured upstream fails as loudly as one that becomes public. Re-derive both from the spec (the `jq` one-liner is in the file header) whenever backend routes land; never patch the predicate one bug at a time
- A public GET skips our session check but still forwards the caller's token when present, so `likedByMe` / `bookmarkedByMe` keep resolving for signed-in readers
- **Upload limits are FETCHED, never hard-coded.** The size caps and the content-type allowlist belong to the backend and are published on `GET /uploads/limits` (public). `lib/upload-limits.ts` reads them once per page load (memoised, silent, retried on the next attempt) and `lib/upload-rules.ts` validates against them; `FALLBACK_LIMITS` exists ONLY for a failed fetch and must be kept equal to the service's current defaults. They used to be hand-copied constants in both repos — two owners of one contract, whose two failure modes we shipped both of: a composer refusing a photo the service would have stored, and a 300 MB upload that runs to completion and then fails. Neither showed up in review or CI. Client validation still runs BEFORE any byte is sent and its message names **both** the cap and the file's actual size — it is the fast, specific error, not the source of truth
- **`maxVideoSeconds` is ADVISORY — we are the only thing that checks it.** The backend publishes it on the same contract but enforces nothing: reading a duration means demuxing the file, and on the presign path the service never sees the bytes. `readVideoDuration` (`lib/video-duration.ts`, DOM half) + `validateVideoDuration` (`lib/upload-rules.ts`, pure half) run in the composer before upload and name both the limit and the clip's real length. A duration we cannot read is **not** a rejection — blocking a valid file because our own probe failed gives the user an error they can't act on, and the byte cap still applies. Never describe this as enforcement
- Query keys are tuples: `["ms","feed",lane]`, `["ms","stream",id]`; mutations invalidate subtrees
- Monetary/KASH amounts are decimal strings end-to-end — never parseFloat for arithmetic, only for display formatting

Gold-for-currency is a real convention carrying real information, so it survived the sweep deliberately; the token is named for what it is so it cannot be reused as decoration. **If a surface is not currency, it does not get this token** — VIP tiers, "premium" and "top-ranked" are all purple now
- Greyscale ramp; panels `#0a0a0a`; semantic green `#7ce7b0` / red `#f6a5a5` for value deltas only
- Type: Geist (body, weight 500), bold display face with `-0.01em` tracking exposed as `ws-display`
- Surface utilities: `ws-card` (22px radius, 5% white fill, 12% white border, inset top highlight), `ws-inset` (16px radius, black/35 fill), `ws-glass` (6% white + backdrop blur), `tnum`
- **A Figma frame gives you the CONTENT box; the whitespace around it is yours.** A spec that says "39px row" with a 38px avatar in it is describing content, not the row — built literally it leaves half a pixel above and below, the avatar touches both edges, and the list reads as one solid block. List rows carry their own vertical padding (`py-3`, so a 38px avatar lands in a ~62px row) and the divider spans the **full width beneath the padding**, never hugging the content. Cramped list rows are one of the most common ways an interface reads as unfinished, and no measurement in the file will tell you — check every row built to a content height
- Rounded/pill shapes, radial-gradient page washes, respect `prefers-reduced-motion`

## Buttons (one size scale)
- **Button GEOMETRY has ONE source of truth: the `ws-btn-{sm,md,lg}` and `ws-iconbtn-{sm,md,lg}` size utilities in `app/globals.css`.** They carry height + inline padding + font only. The `ws-btn-*` COLOUR utilities (`create`/`silver`/`arena`/`welcome`/`follow`/…) carry fill only. A button is therefore **one colour class + one size class + a radius class** — never a hand-written `h-*`/`py-*`/`text-*`/`size-*` again. `components/ui/button.tsx` consumes the same size utilities, so `<Button size=…>` and a hand-rolled `<button>`/`<Link>` render identically; use `<Button>` where a React component is natural, the utilities directly on `<Link>`/`<a>`/exotic markup.
- **MOBILE-FIRST, 44px touch floor.** The base declaration is the touch size (Apple's 44pt); `@media (pointer: fine)` shrinks to the design's desktop size — do not add `pointer-coarse:h-11` at call sites, it is baked in. Text: `sm` 44→32, `md` 44→40 (default), `lg` 48. Icons (square): `sm` 44→32, `md` 44→36, `lg` 48. So on a phone every button is **44 or 48px, period**; desktop is unchanged from before.
- **Radius is NOT in the size utilities** (tailwind-merge can't see inside a custom `@utility`, so a baked radius silently collides with a call site's own `rounded-*`). Set it explicitly, and only two values: `rounded-full` (pills) or `rounded-xl` (12px, squared / full-width). Icon buttons use the `ws-iconbtn-*` utility (it owns width+height) plus `grid place-items-center`; never `h-N w-N`.
- **Chips are not buttons.** `Pill`, `ChipShell`, `RoleChip`, `LiveBadge` (`components/ui/badge.tsx`) are single-size identity/status capsules and stay out of the scale.
- **Design-locked exceptions** keep bespoke geometry and are allowlisted: `FollowPill` (Figma 78×38, test-pinned), `CreateFab` (52.79px), `ws-btn-postgist` (gradient-border box math), the featured arena hero CTA, and the measured pins in `shell-invariants.test.ts`.
- **The ratchet: `lib/button-sizing.test.ts`** counts pressable controls (`ws-press` + an ad-hoc height, no size utility) and fails if the count rises above `RATCHET_MAX`. Lower `RATCHET_MAX` as each migration batch lands (baseline 103, target 0). A new ad-hoc button fails CI — reach for a size utility or `<Button>`, or (for a real exception) add the file to `DESIGN_LOCKED`.

## Counts, badges and unread
- **Never derive a badge from a loaded page.** `GET /me/unread` answers `{ messages, notifications }`, both global, in one call — `hooks/use-unread.ts` owns it and polls at **45s**. Anything that changes a count locally (send, mark-thread-read, mark-notifications-read) calls `useRefreshUnread()` so the badge moves immediately; the poll only catches other people's activity
- **`isFollowing` is optional, never defaulted.** `undefined` means "this payload does not carry the follow edge", which is not the same as "you do not follow them" — `GET /spotlight` omits it entirely today. Defaulting it to `false` made every spotlight refetch stamp "Follow" back over a follow the viewer had just made. Follow controls read `useIsFollowing` (`features/profile/lib/follow-state.ts`), which layers the session's own click intent under the server's answer: the server wins the moment it carries the field (so nothing changes when the backend ships it), the intent only fills the gap when it does not, and with neither the answer is `false` — a missing field can never render a fabricated "Following". The decision itself is pure and pinned in `lib/follow-resolve.test.ts`
- `GET /categories` counts are authoritative and `real-world-assets` / `prediction-markets` return `count: null` **by design** — other services own that data. Null renders as an em-dash, never `0`
- The category rail renders the API's own labels and order; `PRESENTATION` in the rail maps `key` → href + glyph only

## One app, two addresses
- **square.tsionark.com is the standalone Square and must not change.** The same app is ALSO shown inside Ark at `www.tsionark.com/square` (a Next.js Multi-Zone beside WSWS). They are two builds of this repo, told apart by ONE build-time variable, `NEXT_PUBLIC_SQUARE_BASE_PATH`: unset for the standalone project, `/square` for the project Ark mounts. Any other value fails the build (`parseBase`)
- Routes stay in `app/`, files in `public/`. The Ark build rewrites `/square/…` onto them (`beforeFiles` in `next.config.ts`); the standalone build has no rewrites and no redirects. Never move routes under `app/square` again: that changes every standalone address. `basePath` is not used: it would prefix the standalone build too, and a variable-driven rewrite keeps one set of routes for both
- **Every hand-written address goes through `lib/square-path.ts`**: `sq()` for a route, `asset()` for a public file, `api()` for a BFF endpoint. All are no-ops in the standalone build, idempotent, and leave foreign URLs alone. `/_next/static` is prefixed by `assetPrefix` and `/_next/image` by `images.path` (both set only in the zone build), nothing else is
- **Never prefix an upstream path.** `msApi.get("/me")` is the service's path, not ours
- **Pathname checks compare LOGICAL paths**: `stripSquare(usePathname())` first, then compare against `/messages`, `/auth` and so on. It accepts both the prefixed and the rewritten form, so a server render and the browser agree. Nav config `href`s stay logical and are wrapped with `sq()` only where the link renders
- Share links are `${window.location.origin}${sq(…)}`; metadata uses `SQUARE_CANONICAL_ORIGIN` when set (Ark project only)
- **It is a Next.js Multi-Zone, not a Vercel microfrontends group**: WSWS's `next.config` rewrites `/square` and `/square/:path*` to the zone deployment, which is a second Vercel project from this repo with `NEXT_PUBLIC_SQUARE_BASE_PATH=/square` (plus `SQUARE_CANONICAL_ORIGIN`). ## Stories (Instagram pattern)
- The rail groups posts **by author** — one tile per person, a tap plays that author's set oldest-first, then rolls into the next author. `Your story` always leads with a `+` badge and points at `/?compose=story`
- **The strip carries live broadcasts as well as stories, and they are different objects.** Order is `Your story` → **live** → **the server's story order, unchanged**: live is the highest-urgency thing on the square and the only entry that expires while you look at it.
- **`GET /stories?scope=all`, never `scope=following`.** `following` returns only your own stories on an account that follows nobody, which made the rail look broken to every new user. `all` is server-ranked — own, then followed, then everyone, each band newest-first — and **that order is authoritative: the rail must not re-sort it**. An earlier client-side unseen-first sort flattened the bands, floating a stranger's unseen story above a friend's. Sorting unseen-first *within* a band is not possible either, since the payload carries no band marker. Seen state drives the **ring** only (silver vs drained), never tile position — which also stops the rail reshuffling under the viewer as they watch A live tile links into `/live/:id` (or `/studio/:id` when the viewer is the host) and **never** opens the 5-second story viewer; seen/unseen `localStorage` semantics are stories-only, since a stream is live or it is not in the strip at all. Live entries come from the **`live` feed lane** (`useFeed("live")`), which Home already fetches for the featured hero — so the strip costs no extra request and the rail stays inside the feed slice. That lane also carries scheduled activities and not-yet-started streams, so `status === "live"` is a load-bearing filter: **scheduled is not live**, and no viewer count is rendered because the list payload carries only `peakViewers`, never a current one
- The strip's live marker is `--color-live` `#ff0b0b` — the design's solid pill on the tile's bottom edge plus the same red at 40% as the tile ring (`ws-story-live`). This is the **strip only**; the live identity everywhere else is still `LiveBadge`, the black pill with a pulsing silver dot. It is deliberately not `--color-like`: a liked heart is not a broadcast
- Unseen carries the `ws-story-ring` gradient (silver, not Instagram's pink/orange); seen drains to `ws-story-seen`. `ws-story-gap` is the black ring/avatar gap that makes it read as a ring
- Seen state has no backend field: it lives in `localStorage` behind a `useSyncExternalStore` with an empty server snapshot. Every storage access is try/caught
- The viewer is a 9:16 card — per-story progress segments, hold-to-pause, left-third/right-two-thirds tap zones, arrow keys, desktop arrows outside the frame. Artwork-less stories get the seeded `GradientThumb` plus a lift and top/bottom scrims. It is a `role="dialog" aria-modal="true"` that takes focus on open, traps Tab and hands focus back to the tile it was opened from; the desktop arrows are `aria-hidden`/`tabIndex={-1}` because they duplicate the tap zones exactly and, unlike the zones, do not exist below `lg`
- **The viewer's clock, traversal and audio rules are pure, in `lib/story-playback.ts`.** They were inline arithmetic and ternaries inside the component, which is why every bug below shipped: none of it could be looked at without a browser. `lib/story-sound.test.ts` still reads source, but ONLY for the JSX wiring that has no pure half — which `<video>` is bound to the sound setting, which is hard-muted, and that hover is bound to `pointermove`. Everything else is pinned behaviourally in `lib/story-playback.test.ts`
- **Opening a story silences the rest of the page, and closing hands it back.** The feed pauses its clips with an `IntersectionObserver`, and an observer measures the VIEWPORT, not what is stacked on top of it — so a feed video 60% on screen went on playing, with sound, underneath a story that was also playing with sound. `mediaToSilence` collects only what was actually playing and returns it, because that list is also the undo: on close the viewer restarts exactly what it stopped and nothing else. The body is scroll-locked while it is open for the same reason — scrolling the page behind would move feed clips through the intersection that starts them, i.e. start a second soundtrack behind an open story
- **Closing pauses the viewer's media SYNCHRONOUSLY.** `AnimatePresence` keeps the viewer mounted through its fade-out, so an effect cleanup is far too late and the story went on talking over the closing animation. Every exit — the X, Escape, the author link, the CTA, the end of the last story — goes through one `close()` that pauses both `<video>` elements first
- **A story is held for REASONS (`pressing` / `hovering` / `hidden`), never one `paused` boolean.** They overlap, and with a single flag whichever release fired first resumed a story another reason still wanted held. `hidden` is the tab going to the background: `requestAnimationFrame` stops there but a `<video>` does not, so a backgrounded tab used to talk on with its progress bar frozen
- **Hover-to-pause is bound to `pointermove`, NEVER `pointerenter`.** `pointerenter` also fires when an element APPEARS under a stationary cursor, which is exactly what an overlay does — opening a story from a rail tile that happened to sit under the centred card paused it on the frame it opened on, and because the mouse never moved again nothing fired `pointerleave` to release it. The clip sat frozen at 0:00 while its blurred backdrop ran on behind it. A click on a tap zone also clears the hover hold: asking for the next story is asking to watch it. `pointerType === "mouse"` still gates it (a tap fires the hover events immediately before `pointerdown`), and a press is additionally released from the `window` so letting go anywhere resumes
- **The progress bar reads the CLIP's clock, not the wall clock.** Elapsed time is stored in MILLISECONDS, not as a fraction of the duration — as a fraction, the moment a measured clip length replaced the picture beat the same 0.2 meant six seconds instead of one and the bar leapt ahead of the picture. It is also monotonic, so the hand-off from wall clock to `currentTime` cannot drag it backwards. The wall clock keeps running underneath purely as a stall backstop (`hasOverrun`): a clip that has had its whole length plus a grace and still has not finished is broken, not buffering
- **Only `NotAllowedError` turns the sound off.** Sound defaults ON — the viewer only opens from a tap, which is the gesture the autoplay policy asks for — and a refusal drops to muted so the story plays rather than freezing on its first frame. But `play()` also rejects with `AbortError` whenever a pause or a new `src` overtakes it, which happens every time the reader taps through quickly, and answering that the same way silenced the app after three taps. `isAutoplayRefusal` is the whole difference between a working fallback and a viewer that goes quiet for the session
- Tapping back on the FIRST story replays it. It used to close the whole viewer, which reads as the app deciding you are done because you asked to see something again
- **Story media is contained, never cropped.** The frame is 9:16 but a story can be any ratio, so `object-cover` sliced the ends off every landscape photo. Media renders `object-contain` over a blurred, over-scaled (`scale-125 blur-2xl`) copy of itself — the Instagram/WhatsApp letterbox fill — so the card stays full-bleed without losing content. The blurred copy is `aria-hidden`; both layers sit under the tap zones (z-10) and the progress/header chrome (z-20). This is the **viewer** only: the timeline's `post-card` still crops to a ratio deliberately. On a clip the fill is the same file decoded a second time, so it is hard-muted (bound to nothing) and is paused, resumed and re-seeked with the clip it fills for — left running on its own it drifted out of step with the picture in front of it the first time anyone held the story, and it was the only thing still moving while the clip was frozen. Both layers are keyed on the story id so turning the page builds a new element instead of swapping `src` on the old one: a reused element carries the previous clip's `currentTime`, which is now the clock the progress bar reads

## Explore
- **The page IS the design: search field → ONE chip row → card grid.** It used to open with a helper line ("Find people, posts, live streams and ARK Store products.") and a hand-written list of other surfaces to visit (Home feed / Live / ARK Store / Citizen Spotlight) — interim scaffolding from before the grid existed, which sat *above* the design and pushed it below the fold. Both were deleted on the 2026-08-26 revision. **Do not reintroduce them**, and do not blend old scaffolding with a shipped design: remove ours
- The row is `Add +` · For you · People · Posts · Shows · Streams · Products. **`Add +` is not a tab** — it opens the topic picker — which is also why the row is not a `role="tablist"`: a tablist whose children are not all tabs is a broken ARIA contract, and `role="tab"` promises a `tabpanel` that does not exist. Selection is `aria-current`, as the lane tabs use
- **The chip does double duty and the two meanings are pure functions in `lib/explore-tabs.ts`**, not inline ternaries: `exploreTabSearchType` (which `?type=` a search narrows to) and `exploreTabTopics` (which topics apply). `For you` and `Shows` are **not result kinds** — both search `all`; mapping them to a type would silently drop three quarters of the matches. **`Shows` is a TOPIC** from the backend's own vocabulary, not a fifth search type the service does not have
- **Explore must show real content before any choice is made.** With no query and no topic, the grid pages through everything we have — pictures *and* video — because Explore is where people land before they have an account and an empty grid there is the worst possible first impression. Signed-out included: `/feed`, `/search`, `/streams` and `/topics` are all public GETs
- **EVERY tab is populated on arrival.** For you and Shows list the media grid, Streams the live list, People the profile directory, Posts the general feed lane, Products the ARK Store. A discovery surface that opens as a prompt to go and find something is not a discovery surface — there is no longer any "search first" empty state, and adding one back is a regression
- **People, Posts and Products are ROW LISTS, not filtered grids** (`exploreTabIsRowList`): rows from their own paged routes, replacing both the grid and the search results. Each reuses the one component for its object — `PersonRow`, `PostCard`, `StoreItemCard` — composed in through route slots, never restyled per surface
- **`BrowseList` (`components/ui/browse-list.tsx`) is the shared shell for those lists**, extracted at the FOURTH call site rather than the second: loading skeletons, error-with-retry, the 404 "not deployed" branch, a designed empty state, the infinite-scroll sentinel and the next-page spinner, repeated four times, is a real shape. It deliberately does **not** abstract the query — each tab has its own endpoint, key, parameters and schema, and a `useBrowseQuery` factory would hide the part worth reading at each call site to save four lines. The shell is the duplication; the query is not
- **`/feed` and `/store/items` take no `q`.** So on Posts and Products a query falls through to `/search?type=…` rather than narrowing the browse list — the one place the "one list, one cursor" rule does not hold. `q` on both would fix it, as it already does for `/profiles`
- **`GET /profiles` is the people directory**: public with optional auth, `q` / `sort` / `cursor` / `limit`, `sort` being `followers | recent` and defaulting to followers. Nothing else could populate a People tab — `/search?type=people` deliberately returns empty for a blank `q`, `/spotlight` is a short ranked leaderboard, and `/admin/profiles` is admin-only. **Never fake a directory** from a wildcard query or a dressed-up spotlight; the tab was built against this contract and shipped dark, 404ing to a quiet empty state, until the route landed
- **The viewer is filtered OUT of the People directory** — you are not someone you can discover, and a row whose Follow button is missing reads as broken rather than deliberate. **This is scoped to the directory only**: you still appear in followers/following lists and in search results if someone searches your name, because those are statements of fact, not a feed of people to go and find
- **The server does it, and `lib/people-directory.ts` is GONE.** `GET /profiles` excludes the authenticated caller, so the client-side filter that stood in for it — the module, its test and the call in `discover-screen` — was deleted together, as its own header said to. The evidence that settled it is the service's e2e asserting BOTH halves: the same id absent for a signed-in caller and present for an anonymous one, which is the distinction no request from the client can show. **Do not reintroduce a client-side version "just in case"** — two layers doing one job is how the server-side fix stops being verifiable
- **`PersonRow`'s own-row guard is separate and stays.** It suppresses the Follow button wherever you legitimately appear — search results, followers lists — and is not the directory filter in another form
- **`sort` is the SERVER's job.** `followers` opens the tab on the people worth finding rather than on insertion order. The client never re-sorts a paged list, because sorting one loaded page is not sorting the list
- **The `/profiles` COLLECTION is public in `isPublicGet`, and that is load-bearing.** People is a discovery surface that must list for signed-out visitors, with the sign-in invitation only on Follow. `lib/api/public-routes.test.ts` pins the collection shape — this is exactly how `categories`, `search` and `topics` each reached production gated at 401
- **Topics are sorted by the backend's `sortOrder`, explicitly** (`lib/topic-order.ts`). The served array happens to be in that order today; relying on incidental array order breaks silently the day somebody inserts a topic in the middle, and it breaks in the UI rather than in a test. The sort is stable, so ties keep the served order, and it copies rather than sorting the cached array in place
- **`/search` returns `topicFilter` and the UI must surface it.** `{topics, appliedTo, excluded}` — people are **never** topic-filtered upstream, because a person is not filed under a topic. Without saying so, a reader who filtered by a topic and saw no creators would conclude there were none. Rendered only when a filter was actually applied and something really was excluded — never as standing furniture. `null` means "the question did not arise", not "nothing was excluded"
- **People are listed by `PersonRow`, one component, everywhere.** Avatar, display name, `@username`, the three identity chips, and a follow control. It lives in the profile slice (which owns follow) and is composed into Explore through a route slot. Build any future people list on it rather than styling a second variant — that is how two follow controls with two different behaviours end up shipping. The follow control reuses `useFollow` unchanged: optimistic with rollback, `useGate` for the sign-in invitation, `useIsFollowing` so a missing `isFollowing` can never render a fabricated "Following", and hidden on the viewer's own row via `useMe` (compared, not assumed impossible — you can match your own search)
- The design draws only the resting **Follow** pill (60×24, white, black label). **Following** is its inverse — transparent with a white/20 hairline — so a followed person is unmistakable at a glance and can never be misread as the primary call to action
- **Follow invalidation is one shared list**, `invalidateFollowSurfaces` in `lib/api/invalidate.ts`, beside the identity and content sets. It was written out inline in `useFollow`; any surface that grows a follow control needs the identical set, and a second copy drifts silently — the symptom being a Follow button that stays wrong until something else happens to refetch
- The topic picker renders from `GET /topics` and **never** from an array in the component, so a new topic ships from the backend alone. Only the per-key glyph is a local decision, with a neutral fallback for a key the client has not seen
- Interests persist via `PUT /me/interests` and invalidate the feed and Explore, because a saved interest that does not change what you see reads as a no-op. Signed-out readers can choose; the sign-in prompt appears at save, which is the point it is actually required
- **Live counts are `viewerCount` ONLY, never `peakViewers`.** `viewerCount` is absent on list rows and therefore NULLABLE, not `0` — "no live count available" and "nobody is watching" are different claims. `peakViewers` is a historical high-water mark and may only be rendered under an explicit "peak" label (the post-live stats panel and the feed's stream cards do this correctly). Presenting a peak as a live audience is the kind of small dishonesty that makes every other number in the product suspect
- **The Explore card's red/grey pill is a LIKE control, not a live indicator — confirmed by the designer 2026-08-26.** It is a heart with its count: `--color-like` when the viewer has liked it, `--color-grey-400` when not. The earlier reading was "red = the stream is live", guessed because Figma 429'd on every attempt; it was wrong, and the wrong guess is recorded here so it is not re-derived. **The colour comes from the `--color-like` token, never the design's literal `#E84A4A`** — the token already holds exactly that red, and it exists so the heart cannot drift per surface. There is **no red/amber discrepancy** with the post card: `--color-like` was amber `#e8b74a` until the 2026-08-25 revision moved it to red `#e84a4a`, so both surfaces already agree. The two hexes differ only by a digit transposition, which is what makes them easy to confuse
- **Only media cards get the like pill; stream cards get a viewer count.** A stream has no like endpoint, so its card carries the one number it genuinely has, behind an eye glyph so the two pills cannot be mistaken for each other. `viewerCount` only — never `peakViewers`
- The pill stops propagation so it never triggers the card's navigation, carries its own label ("Like …"/"Unlike …") because a bare heart is silent to a screen reader, reuses `useLikePost` unchanged (optimistic, rollback, `reconcilePost` so the like lands everywhere the post appears), and gates signed-out visitors into the sign-in invitation rather than an error. `likedByMe` is read from the server and defaults to the UNLIKED state; an absent count renders the heart with no number, never a fabricated `0`

## Immersive video viewer (the X/Twitter pattern)
- Tapping a video card opens a full-screen player and scrolling moves through the **other videos in the same selection** — the current chip or the current search. The scroll list is not a copy of the grid's list, it **is** the grid's TanStack Query entry, so scrolling past the loaded page fetches the next one exactly as the grid would. Both of Explore's lists get that property: browse through `videoListKey` (`lib/video-context.ts`) behind the single `useMediaFeed` hook, search through `useDiscovery`, which is already keyed on query + type + topics
- **The grid is media, the viewer is video.** `mediaPostsOf` feeds the cards, `videoPostsOf` feeds the slides, both off the same pages. A **picture opens its permalink**, never the player — a still has no scroll list to join, and a play glyph on it would promise something that cannot happen
- **`useMediaFeed` reads `lane=for-you`, not `reels`, and selects media client-side.** This is a deliberate exception to "never filter a lane client-side", which exists to stop a lane TAB being faked — this is not a lane, it is a grid composed from one. `reels` is video-only and there is no media lane or `mediaKind` filter (`/feed`'s lane enum is fixed). The cost is that a page of 30 mixed items can yield very few media, so `discover-screen` keeps paging until the grid is worth showing. **`?mediaKind=image,video` on `/feed` would make this exact rather than approximate** — ask for it before adding more client-side heuristics
- **One vertical-video implementation, not two.** `PostSlide` was lifted out of mobile Home's `SnapFeed` and is now shared by both. Its playback grammar is `InlineVideo`'s: muted autoplay once 60% is on screen, **pause AND re-mute** on exit, sound only from an explicit tap, and under `prefers-reduced-motion` no autoplay plus native controls. `SnapFeed` gained the intersection gating in the move — it used to `autoPlay` every slide unconditionally
- `VideoViewer` is deliberately **data-free**: the caller hands it `items` and the pager. That is what lets discovery's grid *and* its search results drive it without either slice importing the other
- **The morph is a naming rule, not extra state.** A card carries `view-transition-name: video-<id>` whenever its video is NOT open; the active slide carries it while it is. That gives the View Transition a clean hand-off in both directions and never lets two elements share one name — which aborts the transition outright
- The overlay is not a route: the grid keeps its scroll position underneath, and closing scrolls it to the card of whatever video the reader ended on (`data-explore-card`), never the top
- The open video lives in the URL (`/discover?tab=…&v=<postId>`) so it is shareable and a pasted link opens straight into the viewer, paging forward until it finds the video. `history.replaceState`, not a push — every swipe would otherwise stack a history entry. Saved interests are never pinned into a shared link: they belong to whoever opens it
- Tallies on a slide are **optional and render nothing when absent**. `undefined` must never print as `0`

## Ark-originated streams are WATCH-ONLY here
- Ark broadcasts its own surfaces (casino games today) into Market Square as live streams. **Ark is where people participate; Market Square is where people watch.** A stream carrying an Ark product deep link is therefore a viewing surface, and the onward action is to go and join it in the app that owns it
- `isArkOriginated(deepLink)` in `lib/deeplink.ts` is the test, keyed on `deepLink.kind` against `ARK_PRODUCT_KINDS` — **never on a list of games**. A future Ark surface gets the right behaviour by adding its kind there, with no change to the stream room
- On such a stream the room **hides** the speaker-request control (both the desktop header and the mobile rail) and shows "Join the match in Ark" instead. Hidden, not disabled: the host is mid-match and will never approve a request, so a greyed-out button only invites "why is this off?"
- **Do not re-add the speaker control for consistency with native streams.** It is a dead end there, and `lib/stage.test.ts` fails if either entry point loses its guard
- Everything else about watching is unchanged and first-class: chat, reactions, hearts, viewer count, tickets, gifts. Native Market Square streams (no Ark deep link) keep the speaker-request flow exactly as it is

## Live room (TikTok pattern)
- Three panes: the nav rail, the centre column, and a collapsible LIVE chat column. The stage owns the whole viewport — `AppShell` renders `/live/[id]` bare
- **The rail is the way out of the room, so it can never be absent while the room is in its desktop form.** It runs from `lg` — icon-only at 72px, labelled at `xl` (250px) and `2xl` (304px) — the same collapse `AppShell`'s sidebar uses, and the width band every watch page lands in (YouTube's mini-guide is 72px, Twitch's collapsed rail 50px, expanded rails cluster at 240–256px). It was `xl:flex`, which left 1024–1279px with no rail, no back control and no wordmark. Below `lg` the full-bleed stage carries its own overlaid back chevron instead
- `STREAM_NAV` is **one entry per destination**. It used to carry four labels over two hrefs (Back + Discover LIVE → `/live`, Go LIVE + Creator tools → `/studio`), and marked `/live` `aria-current="page"` on a page that is `/live/:id`. Nothing in the rail is current — the rail only leaves. The footer's Company / Program / Terms & Policies were bare `<p>`s with no routes behind them; only the copyright line is real
- **Theater mode hides chrome; fullscreen fills the screen.** They were the same handler, so the control bar shipped two differently labelled buttons doing one thing. Theater now drops the rail and the chat column, is `aria-pressed`, exits on Escape or the same button, and brings the back chevron onto desktop so the exit survives. Chat's collapse control lives in the **header**, not inside the panel it hides — the in-panel-only version was a one-way door on desktop
- The centre column is a **vertical stack from `lg`**: header → 9:16 player → host handle → gift panel. Below `lg` it collapses to one full-bleed stage with everything absolutely overlaid. Never re-attach the player controls to a dock strip: they overlay the frame's bottom edge, and the `LIVE creator` badge, elapsed time and LIVE pill sit **inside** the frame, not in the header
- The vertical action rail (heart, gift, pulse, chat, share) is the **phone** pattern only. On desktop those actions live in the header (share, more, Subscribe, Follow, ticket), the frame's control cluster (pulse, request-to-speak) and the chat column (floating heart, anchored clear of the composer)
- Chat is **monochrome**: flat rows (avatar, grey name, white message), Host/role chips, no per-author colours or tinted bubbles. Top viewers is a podium — rank 1 large, 2 and 3 stacked beside it
- Player chrome uses real icons (`IconPause`/`IconRefresh`/`IconPip`/`IconFullscreen`/`IconVolume`/`IconChevronDown`), never glyph characters — they align to the same 20px grid as the rest of the UI
- Gifting is governance-gated by `MARKET_FLAGS.liveGifts`. With it off there is no tray, so the dock collapses to the 48px control bar and **all** coin chrome disappears (sidebar `Get Coins`, the balance bar, the tray toggle). Gate on `dockExpanded`, never the raw `giftTrayOpen`
- **A capture failure is never just "denied".** `usePublisher` classifies `err.name` through `classifyCaptureError` (`lib/media-errors.ts`, pinned by `lib/media-errors.test.ts`) into four states with four different remedies: `denied` (NotAllowedError/SecurityError — a permission the user must change), `device-busy` (NotReadableError/**TrackStartError** — another app or browser tab holds the device), `device-missing` (NotFoundError/OverconstrainedError) and `failed` (unknown — show the real message, never a permission prompt). Collapsing these told a guest whose camera was held by a second browser profile to "allow camera access", pointing at a prompt that will never appear. The helper also unwraps `cause`, because LiveKit re-throws over the original DOMException
- **The publisher can never spin forever.** A connect that has not settled in `CONNECT_TIMEOUT_MS` (15s) becomes `timeout`, and every terminal state (`PUBLISHER_FAILURES`) renders a message plus a **Retry** that tears down and re-runs the connect. LiveKit `ConnectionError` and a failed `room.connect` surface their message rather than being swallowed. `RoomEvent.Disconnected` only means `failed` *after* the attempt settled — during connect it is the timeout's job
- **Camera failure falls back to audio-only rather than failing the join.** If video cannot be acquired but the mic can, the guest joins with audio, `audioOnly` is true and the panel says "Joined with microphone only — camera unavailable". `toggleCam` is the recovery path: `setCameraEnabled(true)` re-acquires on demand, so video comes up once the device frees, and its own throw is classified too instead of rejecting unhandled. Only when *both* fail is the join refused
- **Cross-product sharing is a PREFILL, never an auto-post.** Ark products link to `/?compose=1&link=<kind>:<ref>` and the composer opens with the thing attached; the person edits and publishes it themselves. The reason it is a URL and not a consumed event: the eight cross-service routing keys Market Square already consumes carry **wallet addresses, not user ids**, so nothing off the broker can be attributed to a profile — it can only ever be an impersonal platform card with no author, avatar or replies. A URL settles authorship before the request is made, and no other team has to change an event payload. Every parameter is hostile input: the kind is an allowlist, `external` is `http(s)` only (that ref becomes an anchor `href` in a published post — `javascript:` there is stored XSS wearing the author's name), everything is length-capped, and a rejected link drops its label so a name never sits beside something that is not there. A bad share opens an EMPTY composer, never a blocked one. Parsed in one place (`lib/compose-prefill.ts`, pinned by its tests) and read through one hook, because two readers is how a validated parameter becomes an unvalidated one on the surface nobody remembered
- **Media is CONTAINED, never cropped — `MediaFrame` is the one rule.** `object-cover` fills a box by discarding what does not fit, and in a full-viewport slide that is brutal: a 16:9 photo in a ~9:19 slide loses most of its width, which is how a scoreboard arrived as a single cropped digit and a caption lost its first and last words. The author framed the shot; the feed does not re-frame it. `object-contain` alone is not the answer either — hard black bars read as a broken image rather than a deliberate one. So the media is contained and the leftover space is filled with a scaled, blurred, dimmed copy of the same frame, held at `black/55` because the ambient layer is ground, not content, and competes with both the media and the white furniture over it. When the ratios already match — a portrait clip in a portrait slide, which is most of them — `contain` and `cover` are identical and the ambient layer is never seen: it costs nothing in the common case and rescues the uncommon one. A clip with no poster falls back to the neutral ground rather than decoding a second copy of the video purely to blur it
- **The host must be able to run the stage FROM A PHONE.** The request queue lived only in the cockpit's desktop right column (`hidden … lg:flex`), so a host broadcasting from a phone — most hosts — could not accept anyone: a viewer could ask and nothing on the host's screen could say yes. Mobile now gets a `GUESTS` button in the same right-edge rail as mic/camera/chat, carrying a pending count, plus a **toast on arrival** with a Review action. A badge alone is not a notification: the host is looking at their own camera, not at chrome, so an arrival has to announce itself. The toast is keyed on request id and seeds silently on first load, so it fires once per request and never re-announces on a 3s poll tick
- **The Guests sheet renders at the cockpit ROOT, never inside the mobile rail.** The rail sits in an `lg:hidden` overlay, so a sheet mounted there would vanish mid-decision if the viewport crossed to `lg` — rotate a tablet while approving somebody and the dialog disappears with the decision half-made. And it is a SHEET, not a route: leaving `/studio/:id` unmounts `usePublisher`, tearing down the LiveKit room and ending the broadcast. Never put host controls behind navigation
- **It is not `PersonRow`.** That row links to `/u/[username]`, and a host who taps a requester's name mid-broadcast navigates out of the cockpit and ends their own stream. The identity composition is reused (avatar, name, handle, the three chips); the navigation is precisely what must not be
- **One resolve path.** Mobile calls the same `useResolveSpeakerRequest` the desktop cockpit does, and the same `useSpeakerRequests` key, so there is one poll, one cache and one set of invalidations. Approve/decline/remove are the backend's own actions — no second endpoint and no client-side state machine
- **Tile removal is an explicit button, not long-press.** Long-press has no affordance, nothing tells a host it exists, and on a video tile it collides with the browser's own long-press menu. The button was already always rendered (hover only intensifies it) so it worked on touch; what it lacked was a target — the hit area is now 44px on touch and the design's 28px from `lg` up, with the visual circle unchanged
- **The host's queue shows `approved`, not "on stage".** Approval is a decision the host made; whether the guest's browser actually acquired a device and connected is not in the speaker-request payload, so a confident green "is on stage" was asserting something unobservable while the guest sat stuck. Real presence needs the room's remote participants threaded from the publisher into `SpeakerRequestQueue` — not wired yet
- `Suggested LIVE creators` reads the live stream list minus the current room; the header identity falls back to the stream title when `owner` is not hydrated (list and detail payloads do not always carry the profile). In the collapsed rail it degrades to avatars alone, so each row carries its own `aria-label` — the name text is `display:none` there and cannot supply the accessible name

## Money that MOVES (buying KASH, buying a `$TICKER`)
- Two upstreams besides Market Square, each behind its own BFF and its own client: the **KASH engine** (`app/api/kash/[...path]` → `${WSAPI_BASE_URL}/v1/kash`) and the **routing provider** for token buys (`app/api/dextopus/[...path]`). Neither goes through `msApi`, and both pass `breaker: false` — the circuit breaker's open state renders "Can't reach Market Square right now", and three 502s from a KASH balance poll must not tell the feed, messages and notifications that the square is down
- **The KASH proxy's ownership check is the whole reason it exists.** The engine has NO auth: it keys every account read and every purchase on the wallet in the path or body, and `GET /v1/kash/accounts/<anything>` answers 200 to the open internet — verified live. So the proxy enforces two things on every non-public path: a verified session, AND that the named wallet is the session's own **embedded** wallet, resolved from the issuer server-side (`getRequestWallet`: Decane's address endpoint, or Privy `getRequestUser` → `embeddedEvmWallet` for a legacy session). A wallet the browser named would make the gate decorative. Paths outside the allowlist are refused rather than blind-forwarded — `conversions`, `activities`, `settlements`, the sell desk and everything else 404 here
- **Embedded ONLY, unlike wsws.** wsws falls back to the first linked EVM wallet when there is no embedded one; `lib/wallet.ts` deliberately does not. That fallback makes the server's answer and the client's diverge for anyone who has linked an external wallet — the browser asks about its embedded address and the server proves a different one — so the gate refuses a legitimate request. No embedded wallet means no KASH identity and the surfaces go quiet
- **Amounts are decimal strings or `bigint` base units, end to end.** `lib/erc20.ts` converts (string surgery + `BigInt`, never `Number`) and encodes the ERC-20 transfer by hand — dependency-free so `node --test` pins the exact calldata against a known vector. `lib/kash-amount.ts` compares two amounts without either becoming a float. More precision than the token holds THROWS rather than rounding: silently dropping a decimal changes the sum in a direction nobody authorised. The ONE deliberate float is `estimateTokenAmount` (`lib/ticker.ts`), a preview under the words "at today's price" that is never sent, signed or compared to a balance
- **Every buy surface shows what the reader can SPEND before it asks them to spend it.** USDC on Base funds every purchase, so `hooks/use-usdc-balance.ts` reads it with one `eth_call` through the session-gated RPC proxy — the token contract's own integer, not a portfolio service's assembled figure, because this number decides whether a buy button is offered and it has to be the same number the transfer is checked against. A sheet that asks for an amount and only reveals at the payment that the wallet is empty is the flaw the tip sheet had before it showed a KASH balance
- **The buy button carries the reason it is disabled** (`Enter an amount` / `Minimum $1` / `Not enough USDC` / `Finish this purchase`), which is wsws's own pattern. A dead control beside a small grey line makes the reader hunt for the cause; the thing they are reaching for should be the thing that explains itself. `Finish this purchase` outranks every other label, because a held payment means their money has already moved and that is what they most need to be told
- **The balance is TAPPABLE and fills the amount**, again as wsws does — "spend what I have" is one press rather than a figure to copy by hand. It is safe to fill from because `formatUsdc` floors to cents, so it can never ask for more than the wallet holds, and the KASH sheet clamps it to the engine's own maximum so the shortcut cannot produce an amount the service will refuse
- **Unknown is not zero, in both directions.** `decodeUint256` answers null for an unreadable word (a bare `0x` is what a call to a non-contract returns) and `canAfford` returns TRUE on a null balance: blocking a funded buyer behind a request that has not come back is worse than letting the payment fail honestly at the wallet, and the chain is the only thing that can truly refuse a transfer. A known ZERO is different again and is said plainly — "you'll need USDC on Base" — before an amount is chosen, because no amount would have worked
- **A payment that succeeded must survive a failed credit.** Buying KASH is send-then-credit and buying a token is quote-send-then-settle; in both, only the first step moves money. `lib/payment-hold.ts` decides which attempt a receipt belongs to and how long it stays reusable; `lib/payment-store.ts` keeps it in **sessionStorage**, not a ref — wsws's ref survives a failed credit but not the page reload somebody does when a payment screen appears to hang, and with the receipt gone the next attempt is a SECOND payment. The key CANONICALISES the amount, so `10` and `10.00` are one attempt rather than two payments. It is written BEFORE the confirmation wait, cleared on success, and cleared on the engine's `payment_already_used` CONFLICT — which is a success wearing an error's clothes, not a failure
- **Idempotency keys are minted where intent begins**, once per attempt, and forwarded verbatim by the proxy. A key generated per request is a new key on every retry and protects nothing
- **The buy button is never optimistic.** It is disabled through signing, confirming and crediting, and its label says which. A live button during an in-flight transaction is a second payment waiting for an impatient tap
- **A hash is not a payment** (`lib/tx-receipt.ts`): `eth_sendTransaction` resolving means a node accepted it, not that it was mined, and a reverted transaction has a receipt and moves nothing. A receipt with no recognisable status is PENDING, never success
- **The one-signature desk flow vs. the two-step flow is the ENGINE's decision.** `GET /desk` answering selects the desk; a 502 ("on-chain desk endpoints are not configured" — production's answer today) means no desk exists and the two-step pay-then-credit flow applies. A desk that exists and is `paused` is a deliberate halt and must stop buying, never fall back. `status.coverage.state` is REDEMPTION solvency (`paused` in production) and must never gate buying — a purchase adds to the treasury rather than drawing on it
- **Chain values come from `status.chain` at runtime**, never hard-coded: the payment address, the USDC address and the chain id. A wrong token address is a transfer into nothing and a wrong payment address is a gift to a stranger, so a missing one refuses the purchase rather than guessing
- **Solana destinations are not offerable** (`lib/buy-routes.ts`), excluded by name rather than by omission: delivering there needs a Solana wallet, an SPL transfer and an RPC that this app does not have, and a route we cannot receive on would take USDC on Base with nowhere to put the token. Everything else is wsws's own vetted chain list, unshortened — trimming it silently drops coins that are perfectly deliverable. `$BTC` works: it is delivered as cbBTC on Base, and the sheet says so
- **A pinned coin is only itself on its native chain.** The live catalogue offers SOL twice — native on Solana, and an ERC-20 "SOL" on Base — so `CANONICAL_CHAIN` pins it and `$SOL` offers nothing rather than the wrapper. Selling somebody a Base token that tracks SOL under the ticker they tapped is a substitution only noticed later, in a wallet that does not hold what its owner thinks. Legitimately multi-chain assets (ETH on its L2s, native USDC issuances) are deliberately absent from that map: those really are the same asset. **Checked against the live catalogue, not assumed** — the wrapper was being offered until it was
- **Gas is SPONSORED, and it is wsws's stack rather than a second one.** Every payment is signed by the reader from their own embedded wallet (ADR-0005, non-custodial), which costs ETH on Base — and an embedded wallet funded with USDC alone has none, so an unsponsored flow fails for exactly the readers it is built for. `lib/trade/sponsor.ts`, `lib/trade/sponsored-evm.ts`, `lib/trade/receipt.ts`, `config/alchemy-bso-evm-networks.json`, `lib/server/alchemy-bundler.ts` and both proxy routes are ported from wsws unchanged: the EOA is upgraded IN PLACE via EIP-7702 to the shared Simple Account implementation, so sponsorship never moves funds to a separate smart-wallet address, and the userOperation goes to Alchemy's bundler through `/api/alchemy-bundler/[network]` where the key and the gas-policy id are added server-side. Both apps run on one Decane identity, so it is one wallet on one policy across both
- **The bundler transport and the read transport are SPLIT, deliberately.** Only the userOperation methods go to the bundler endpoint; every plain node read (`eth_getCode`, `eth_getTransactionCount`, gas) goes to `/api/evm-rpc/[network]`. State reads through the bundler endpoint are slow and intermittently time out, and the `eth_getCode` issued on every send is what hung wsws's flow before the split. Both proxies are session-gated and method-allowlisted — neither may become a generic paid RPC relay, and `eth_sendRawTransaction` is absent from both
- **A receipt is read on a client pinned to the transaction's chain** (`lib/trade/receipt.ts`), never the embedded wallet's ambient provider: the wallet can leave that provider on a different chain, so the receipt would be polled where the transaction never happened and never found
- **The embedded wallet is Decane's, configured the same way wsws configures it.** Both apps run on one Decane identity, so a reader who has signed into either has the same wallet — that is what makes a balance earned in one spendable in the other. `app/providers.tsx` mounts `DecaneKit` with the recovery callbacks (`lib/decane-recovery.ts` + `DecaneRecoveryHost`); without `promptUnlockPassword` a device with no passkey cannot open its wallet at all
- **`showWalletUIs: false`, also matching wsws — so OUR SHEET IS THE CONFIRMATION.** A sponsored purchase is two wallet interactions (the one-time 7702 delegation and the userOperation) and a modal in front of each turns one deliberate act into a sequence the reader has to decode. The consequence is a copy obligation, not a free win: the buy button is the last step, so the sheet must name the amount, the price, the fee, where the token lands and that it cannot be reversed BEFORE the press — and must never say "you'll approve this in your wallet", which describes a prompt that no longer appears
- **A `$TICKER` opens IN-APP.** `components/ui/post-text.tsx` and `coin-chips.tsx` call `openTicker` (`lib/ticker-store.ts`, a module store behind `useSyncExternalStore` — no context, no store library); the shell mounts ONE `BuySheet` through `components/layout/ticker-sheet.tsx`, exactly as it owns the global composer. `components/ui/` cannot import `features/`, and threading a callback through every surface that renders a caption is a prop nobody reads. The sheet is keyed on the OPENING, not the symbol, so reopening the same ticker never inherits a previous order's progress
- Ark's origin still gates the chip: `/api/symbols` fetches the tradeable catalogue from it, so unconfigured means no catalogue, no price and nothing to open — the ticker stays plain text, as before

## Capability flags (`MARKET_FLAGS`)
- One switch per capability in `lib/market-config.ts`, defaulting **OFF** and read from `NEXT_PUBLIC_MS_*`. A flag exists so turning something on later is one line, not an archaeology exercise — so gate at the surfaces, never by deleting the concept
- **A flagged-off surface is VISIBLE and INERT, never a control that looks tappable.** Deleting it silently loses the roadmap ("Replays — coming soon" tells a reader something real); leaving it live tells them a lie. Disabled means a real `disabled` button — unclickable, untabbable, announced — not a dimmed one that still fires. `ColumnTabs` takes `disabled` for exactly this
- **`replays` — recorded playback of an ended stream. OFF because the capability does not exist, not because of policy.** The RECORDING CODE IS FULLY IMPLEMENTED on the service — an egress starts on go-live, is stopped and listed on end, and its URL is written to `replay_url`; none of it is stubbed. What is missing is **THREE INDEPENDENT SWITCHES, each a different person's to turn on**, and `replayUrl` is null until all three line up: **(1)** LiveKit egress actually running — infrastructure, and not even our LiveKit, since market-square uses Ark Stream's deployment on purpose; **(2)** `LIVEKIT_S3_ACCESS_KEY` / `LIVEKIT_S3_SECRET` / `LIVEKIT_S3_BUCKET` on the service — with any one unset the egress still starts but writes to a path inside its own container that nobody can fetch, so the URL comes back undefined; **(3)** `NEXT_PUBLIC_MS_REPLAYS_ENABLED` here — whether anybody is shown it. **The failure mode when somebody turns on ONE of them is that both halves look correct and nothing appears** — the service records to nowhere and honestly reports null, this app correctly draws nothing, and each side reasonably concludes the other is the blocker. Same shape as the coin economy: a capability that reads as shipped from every angle because every piece of it is built. **Before switching it on, confirm a real ended stream comes back with a non-null `replayUrl`** — the flag makes the surfaces reappear, it cannot make the recordings exist. It gates: the `/live` Replays tab (visible, disabled, "Soon"), the `mode: "replay"` player in the stream room (an ended stream says so instead of entering a player with nothing to load), the play badge and "Replay available" label on ended stream cards, the Studio post-live replay card (a statement, not a link), the ticket tier description, the ticket sheet's Replay policy line, the replay line on a ticket receipt, and the end-stream confirmation copy
- **The commercial copy was the important half.** A ticket tier that read "Live access and replay when published" was *selling* a recording that cannot be produced, and the receipt then printed a replay entitlement for it. Anything that takes money must never describe a capability behind a flag that is off
- **`storeNav` — promotion of the ARK Store in navigation. It gates PROMOTION, never the feature.** `/store` and `/store/[slug]` keep working, deep links resolve through `lib/deeplink.ts`, and Explore's Products tab still lists items — hiding an entry must never break a route. It gates: the sidebar entry, the mobile tab bar and the mobile drawer (all three read one `NAV` list through `visibleNav`, so the rule lives in one place), the Explore category tile, and the "Browse the ARK Store" empty-state CTA
- **The Explore category row STAYS when `storeNav` is off — it just loses its link.** `GET /categories` owns the rail's labels, order and counts and that is authoritative; hiding the row would edit the service's own list. Dropping only the destination makes it render inert, exactly as the Ark-app categories do when that app is not configured

## Conventions
- Named exports only (no default exports except Next.js route files)
- `clsx` + `tailwind-merge` via a `cn()` helper
- Loading skeletons + inline error states for every query; empty states designed, not blank
- **Fixtures answer ROUTES; they do not invent CONTENT to make a screen look full.** Demo posts, clips and people added to demonstrate a surface were stripped on 2026-08-26 — the app shows what genuinely exists, and where that is nothing, the designed empty state IS the correct screen. Never re-add content to flatter a screenshot, and never hide an empty tab to avoid one. The fixture *handlers* stay: they must keep answering every route faithfully (topic filtering, `topicFilter`, the follow edge, full post payloads) even when the answer is an empty list
- `.env`: `WSAPI_BASE_URL`, `NEXT_PUBLIC_DECANE_APP_ID`, `DECANE_API_KEY`; legacy `NEXT_PUBLIC_PRIVY_APP_ID` / `PRIVY_APP_SECRET` for the account-link window; `MIGRATION_SERVICE_ENABLED`
- Gates: `pnpm lint && pnpm typecheck && pnpm test && pnpm build` must pass
- Tests run on Node's built-in runner (`node --test`, zero dependencies) over `lib/**/*.test.ts`, using Node 24 native type stripping — hence `allowImportingTsExtensions` and the real `.ts` import specifier in test files

## Do NOT
- Import from wsws-frontend; use any component library; use Redux/Zustand/Context-as-store; put logic in route files; use floats for money; use `any`
